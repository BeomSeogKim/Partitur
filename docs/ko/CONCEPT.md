# Partitur — 개념과 어휘

> 이 문서는 영어 정본 [`docs/CONCEPT.md`](../CONCEPT.md)의 한국어 매핑입니다. 내용이 갈리면 영어 정본이 우선합니다.

## 왜 이 프로젝트가 존재하는가

AI 모델은 계속 좋아지고 있고, 벤더마다 모델이 일하는 스타일이 뚜렷하게 다르다.
Partitur는 모델 지능 위에 또 하나의 지능 레이어를 얹으려는 것이 아니다. 다른 공백을
겨냥한다: **모델·세션·인계(hand-off)를 가로지르는, 오래가는 벤더 중립 조율의 부재.**

Partitur는 사용자가 개발의 각 파트를 스스로 가장 적합하다고 판단한 performer에게
바인딩하고, 다른 performer들이 그 작업에 도전하고, 보완하고, 검증하는 구조를 제공한다.
이 프로젝트는 만든 사람이 매일의 개발에서 직접 필요로 했던 도구에서 출발했고, 이미
여러 코딩 에이전트를 굴리며 각각의 특성을 아는 사람들을 위해 만들어진다. 첫 번째
서약은 그 출발점에서 따라 나온다:

> **단일 AI 벤더에 절대 묶이지 않는다.** 어떤 벤더의 모델이든 하나의 performer로
> 들어올 뿐이고, 사용자는 자기 입맛대로 그들을 편성한다.

## 핵심 가치

Partitur는 **코딩**에 특화한다. 핵심 가치는:

> **말한 문제와 풀린 문제 사이의 거리를 최소화한다.**

에이전트 실패 중 가장 값비싼 부류는 눈에 띄게 망가진 코드가 아니라, 미묘하게 다른
문제에 대한 해답이다. 초기에 스며든 애매함과 오해는 인계를 거칠 때마다 증폭된다.
Partitur가 컨텍스트(score)를 소유하는 이유가 정확히 이것이다 — 첫 확인 질문부터
마지막 검증까지, 그 거리를 짧게 유지하기 위해.

여기서 "말한 문제"는 사용자의 최초 발화를 문자 그대로 뜻하지 않는다. 질문과 해소를
거쳐 score에 명시적으로 확정된 사용자의 의도를 뜻한다. Partitur가 최소화하는 거리는:

```text
확정된 사용자 의도 ↔ 검증된 결과
```

설계 질문이 막힐 때는 하나의 시험이 판정한다:

> "이것이 말한 문제와 풀린 문제 사이의 거리를 줄이는가?"

## 왜 이 이름인가

**Partitur**는 독일어로 **총보**(總譜)다. 오케스트라에서 모든 악기의 파트가 한 페이지에
세로로 정렬돼 있는 악보이고, 이걸 읽는 사람은 오직 **지휘자** 한 명뿐이다. 연주자는 자기
파트만 본다.

이 프로젝트의 본질이 정확히 그 자리다:

> 각 에이전트(Claude Code, Codex, Gemini, Kimi...)는 자기 파트만 알아도 된다.
> **전체상을 한눈에 쥐고, 각자에게 배역을 나눠주는 유일한 자리** — 그게 Partitur다.

이름을 이렇게 고른 이유는 하나다. 이 프로젝트에서는 이름이 설계를 끌고 간다.
막힐 때마다 던지는 질문이 방향을 정해준다:

> "총보를 쥔 자라면 이걸 어떻게 볼까?"

이 질문은 자연스럽게 아키텍처를 **"중앙의 선언적 계획(score) + 파트 분배"** 구조로 수렴시킨다.
에이전트는 연주자일 뿐, 전체를 아는 건 Partitur다.

## 핵심 역할 네 가지

1. **casts (배역)** — 각 파트를 사용자가 가장 적합하다고 판단한 performer에 바인딩한다.
2. **cues (큐)** — 작업을 디스패치하고, 적절한 순간에 진입시킨다.
3. **keeps time (박자)** — 동시성과 파트 간 인계(hand-off)를 조율한다.
4. **holds the score (총보 소유)** — 모든 파트가 파생되는 단 하나의 선언적 계획을 소유한다.

## 구조 모델

Partitur는 작업과, 그 작업을 실행하는 performer를 분리한다:

- **score**는 의도, 제약, movement, 논리적 파트를 정의한다.
- **cast**는 각 논리적 파트를 performer에 바인딩한다. Partitur가 디폴트를 제공할 수는
  있지만, 최종 cast의 주인은 사용자다.
- **adapter**는 performer를 Partitur의 벤더 중립 실행 프로토콜에 연결한다.

score는 보편적인 라인업을 하드코딩하지 않는다. 계획·구현·검증 어느 파트든, 작업
자체의 의미를 바꾸지 않고 다른 performer로 재바인딩할 수 있다.

## 어휘 체계

도메인 용어를 통째로 악보에서 빌려온다. 시스템이 커져도 네이밍이 일관되게 유지되도록.

| 용어         | 음악적 의미            | Partitur에서의 의미        |
|--------------|------------------------|----------------------------|
| **score**    | 완성된 총보            | 선언적 계획                |
| **part**     | 한 악기의 성부         | 한 에이전트의 배역         |
| **movement** | 악장 (작품의 한 부분)  | 작업의 단계 / 페이즈       |
| **cue**      | 진입 신호             | 에이전트로의 디스패치      |
| **tutti**    | 전원 합주             | 브로드캐스트 / 팬아웃      |
| **rest**     | 쉼표                  | 유휴 / 대기 중인 에이전트  |
| **tempo**    | 빠르기                | 동시성 & 페이싱            |

구조 용어는 음악 어휘 옆에 나란히 둔다. 억지로 은유에 끼워 넣지 않는다.

| 용어          | 의미                                                   |
|---------------|--------------------------------------------------------|
| **performer** | 실제로 작업을 실행하는 모델 또는 에이전트              |
| **cast**      | 파트와 performer 사이의 바인딩                         |
| **adapter**   | performer를 코어 실행 프로토콜에 연결하는 벤더 플러그인 |
| **run**       | 특정 score revision을 특정 cast로 실행한 한 번의 기록  |
| **amendment** | score 또는 그 지시에 대한 명시적·버전화된 변경         |

## 설계 원칙

- 연주자(에이전트)는 교체 가능하다. 총보는 **벤더 중립적**이다 — Anthropic, OpenAI,
  Google, Moonshot 어느 진영이든 하나의 파트로 들어온다.
- **권위는 분리되고, 결코 숨지 않는다.** score는 의도·제약·계획된 작업의 권위 있는
  원천이다. event log는 실행 이력의 권위 있는 원천이고, artifact는 생산된 증거와
  결과를 담는다. 벤더 세션은 절대 권위 있는 상태가 아니다 — 값싼 재개를 위한
  캐시일 뿐이다.
- 파트는 score에서 파생된다. 각 파트는 자기 작업에 필요한 의도, 제약, 입력, 전역
  불변조건을 전달받는다. 어떤 performer도 전체에 대한 독자적 재구성을 소유하지 않는다.
- Partitur는 **작은 실행 프로토콜이지, 추론 레시피의 라이브러리가 아니다.** 모델들이
  스스로는 신뢰성 있게 공유할 수 없는 의도·상태·권한·증거를 소유한다. 사용자 의도,
  프로젝트 사실, 파트별 지시를 전달할 수는 있지만, 일반적 사고 패턴·페르소나·벤더별
  추론 요령을 코어에 담지 않는다.
- **미니멀 하네스.** 무엇이든 코어에 들어가기 전에 네 가지 질문을 통과해야 한다:
  더 좋은 모델이 대체할 수 있는가(지능)? 누가 무엇을 해도 되는지를 집행하는가(권한)?
  프로세스·벤더·세션이 죽어도 남아야 하는가(지속성)? 성공 여부를 외부 세계에서
  관찰·검증하는가(증거)? 현재 모델 지능을 보완하기만 할 뿐 나머지 세 기능 중 어느
  것도 수행하지 않는 요소는 코어 밖에 머문다.
- **런타임은 독립적이다.** 벤더 에이전트 옆에서 돌지, 그 안에서 돌지 않는다.
- **의도는 실행 전에 확정되고, 그 후에는 명시적으로 개정된다.** score는 `DRAFT`로
  시작한다. 미해결 질문과 검증 기대(verification expectation)는 해소되거나 명시적으로
  유예(waive)되어야 `FINALIZED`가 된다. 실행 중의 발견이 score를 조용히 바꾸는 일은
  없다. 의미 있는 변경은 버전화된 amendment로 기록된다.
- **검증은 유형화되며, 단일 `passed` 플래그로 뭉개지지 않는다.** 기계 증거, 사람 승인,
  모델 리뷰는 서로 다른 주장을 하며 run 내내 구분된 채 유지된다. 모델 리뷰는 발견
  사항(finding)을 제기할 수 있지만, 결코 기계 검증이나 사람 승인으로 표시되지 않는다.
